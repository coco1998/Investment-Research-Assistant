# 投资会议纪要整理技能

将 ASR 转录稿（飞书妙记/腾讯会议等）整理为专业投资会议纪要。转录稿可能存在识别错误，需要结合上下文和行业知识进行纠正。

## 用户关键词（可选）

用户可以在提供 ASR 转录稿时，附带一组关键词。关键词有两个用途：

1. **确保术语准确**：会议中如果出现了关键词，原文中不要写错（公司名、产品名、技术术语等）
2. **行业背景理解**：用关键词进行搜索，了解该会议所处行业的基本背景，至少知道围绕什么行业展开

收到关键词后，整理纪要前应先搜索了解行业背景，但不要在纪要正文中额外添加搜索到的外部信息，仅在必要时用括号补充说明术语含义。

## 纪要类型判断

根据会议性质自动选择纪要类型：

- **公司交流**：拜访/调研某家公司，与公司管理层/创始人/业务负责人交流
- **专家访谈**：与行业专家/产业链人士的访谈，专家介绍行业情况

如果用户没有明确指定，根据会议内容判断：以公司自身业务为核心 → 公司交流；以行业观点和技术路线分析为核心 → 专家访谈。

---

## 类型一：公司交流纪要

### 标题格式

```
公司名 - 访谈类型 - 日期
```

示例：`Example GenAI Co - 管理层访谈 - 20260515`、`Example Sensor - 创始人拜访 - 20260518`

### 头部信息

用 blockquote（`>`）格式，包含：
- 公司全称
- 如果有被拜访人员的职位或姓名，也需写出
- 录制文件链接

示例：
```
> 公司: Example Sensor
>
> **录制文件：https://example.com/meeting-link
```

### 正文结构

- 按业务维度组织，将散落在对话中的相关信息归拢到同一维度下
- 常见维度：融资情况、团队背景、技术路线、产品情况、商业模式/客户、财务数据、行业观点、商务进展
- **融资进展和商务进展是两个分开的独立板块**，不要合并放在一起
- 维度划分灵活，相似的放在一起即可，不要求维度名称统一
- **不需要写"公司介绍"这种概述性段落**，直接进入实质性内容

### 内容处理规则

1. **过滤寒暄**：删除分析师自我介绍、双方客套、与业务无关的闲聊
2. **只保留公司侧信息**：分析师的问题和评论不保留，只保留公司方的回答和信息
3. **客观还原**：用公司方的原话表达，不做二次加工或主观判断
4. **结构化归纳**：将散乱的对话按维度归拢，同一主题的信息放在一起

## 类型二：专家访谈纪要

### 标题格式

```
行业主题专家 - 专家所在公司 - 日期
```

示例：`AI/AR眼镜专家 - Vivo - 20260522`、`AR眼镜专家 - Example Optics Lab - 20260521`

### 头部信息

用 blockquote（`>`）格式，包含专家背景资料和录制链接：

```
> 公司: 专家当前所在公司
>
> 职位: 专家当前职位
>
> 背景: 按时间倒序列出专家履历，格式为「时间段 在公司担任职位，负责xxx」
>
> 特长: 专家的核心专业领域
>
> 评价: 第三方对专家的评价/推荐语（如有）
>
> **录制文件：https://...**
```

### 正文结构

- 按问题方向/主题分组，每个方向作为一级 bullet point
- 保留问题本身的逻辑框架，但不需要保留逐字问答格式
- 专家对每个问题的回答内容归纳在对应主题下

### 内容处理规则

1. **保留原文观点**：专家的判断、数据、推测原汁原味保留，不添加分析师自己的解读
2. **保留 vivid 描述**：专家用的生动比喻、具体数字、案例细节要完整呈现
3. **过滤寒暄**：开场客套和过渡性对话可删除
4. **按主题归拢**：如果同一话题在会议不同时段被多次讨论，合并到同一主题下

## 通用格式规范

### 层级结构

- **禁止使用 Markdown 标题**（`#`、`##`、`###`），全文只用 bullet point 层级
- **默认使用无序列表 `-`**，仅当信息之间有明确的先后顺序或因果关系时，才使用有序列表 `1.`
- 每一层用缩进（tab）区分父子关系
- 一级维度用 `**加粗**` 标记，作为该板块的视觉锚点

示例结构：
```
- **大主题一**
   - 子要点
      - 更细节的内容
   - 另一个子要点
- **大主题二**
```

### 重点标记

- **加粗**（`**`）：用于维度名称（一级 bullet point 标题）、关键数据、核心判断、重要结论
- **加粗 + 下划线**（`**` + `<u>`）：用于**非常重要且还原会议 vivid 描述的内容**——专家的生动比喻、反直觉观点、原汁原味的精彩表述
- 注意区分：普通的重点信息只加粗即可；只有那些「如果用自己的话改写就会丢失味道」的原话，才同时加粗加下划线
- **括号补充**（``）：用于补充背景知识、数据口径说明、公司/术语的简要解释

### 信息完整性

- 尽可能还原会议的全部实质性内容，不遗漏信息
- 散落但相关的信息点要归拢到同一主题下
- 按信息重要性排序，最重要的内容放在每个维度的最前面
- 如有需要确认的信息或转录稿明显有误的地方，用括号标注（如"需后续确认"）

### 专业术语

- 公司名称、产品名称、技术术语、行业缩写必须准确
- 不确定时需搜索确认，不要猜测
- 英文术语保留原文，中文术语使用行业通用译法

## 质量控制清单

整理完成后，逐项检查：

1. 标题格式是否符合对应类型的规范
2. 头部是否包含录制链接
3. 正文是否使用了任何 Markdown 标题（如有，全部替换为 bullet point）
4. 寒暄和自我介绍是否已过滤
5. 公司名/人名/专业术语是否准确（如用户提供了关键词，关键词中的术语绝对不能写错）
6. 维度名称和重点信息是否加粗，最关键且 vivid 的表述是否同时加粗加下划线
7. 列表是否默认为无序列表 `-`（非有序关系不用 `1.`）
8. 融资进展和商务进展是否为独立的两个板块（不合并）
9. 同一主题的信息是否归拢在一起（而非散落在不同位置）
10. 会议中的实质信息是否有遗漏
11. 是否有分析师的主观解读混入（应删除）
12. 转录稿明显错误的地方是否已纠正或标注
